# Current Architecture

Generated by a read-only repository audit on 2026-09-26. Every claim below was verified against source at that time by tracing actual implementation, not by reading old documentation. File:line citations are preserved wherever the underlying audit captured them; if the codebase has moved since, treat the citation as "verified once, re-check before relying on it." Uncertainties are labeled explicitly rather than guessed.

This app (`propcid_app`) is the Flutter mobile client of the PropCid real-estate platform. A separate React/TypeScript web portal exists and shares the same Supabase backend — the Flutter app frequently ports logic from the portal deliberately, and many source comments cite the portal file/line they're mirroring.

## App Bootstrap Sequence

`lib/main.dart` (before `runApp`):
1. `WidgetsFlutterBinding.ensureInitialized()` (`main.dart:39`).
2. `await dotenv.load(fileName: ".env")` (`main.dart:41`) — loads `.env` from repo root, declared as a Flutter asset in `pubspec.yaml:137`.
3. `Supabase.initialize(url: dotenv.env['SUPABASE_URL']!, anonKey: dotenv.env['SUPABASE_ANON_KEY']!)` (`main.dart:43-46`) — force-unwrapped; a missing `.env` key crashes at startup with no fallback UI.
4. `_registerVoiceAgentTools()` (`main.dart:29-36, 48`) registers the voice-agent tools — **31** registered tool names (see Voice Agent section for the breakdown).
5. `final authProvider = AuthProvider()` is constructed **outside** the provider tree (`main.dart:54`) specifically so `InviteDeepLinkHandler` can read the same instance without a `BuildContext` (comment `main.dart:50-53`).
6. `runApp(MultiProvider(...))` wraps `PropertyApp` (from `app.dart`) — see State Management below.
7. **After** `runApp` returns, `unawaited(InviteDeepLinkHandler(authProvider: authProvider).start())` fires (`main.dart:97-100`) — deliberately after `runApp` so `appNavigatorKey` is attached before a cold-start deep link is processed.

**Observability**: no app-wide production crash/error telemetry integration is present in the Flutter source. No Sentry, no Crashlytics, no `FlutterError.onError`, no `PlatformDispatcher.instance.onError`, no app-wide `runZonedGuarded` — the only `runZonedGuarded` usages are narrow wraps around Razorpay's `razorpay.open()` call. External platform/backend observability, if any, cannot be determined from this repository. This means the repository's own test results, incident log, and known-issues documentation are the only record of app health available here — none of it substitutes for production runtime telemetry (crash rates, error frequency, affected-user counts in the wild), whether or not such telemetry exists elsewhere.

`lib/app.dart` (`PropertyApp`, a `StatelessWidget`) returns one `MaterialApp`:
- `theme: AppTheme.lightTheme` only — no dark theme/`themeMode` wiring found.
- `home: const SplashScreen()` — the app always cold-starts into Splash.
- `builder:` wraps every screen in `PendingInvitationGate` → `Stack` of `AppGlassBackdrop` (background), the actual screen, `CompareFloatingBar`, `FloatingAiOrb` — these three overlays sit above every screen, outside the Navigator's own subtree.
- `onGenerateRoute:` — see Navigation below.

**Repository-maintenance note, not architecture**: at various points this working tree has contained loose `.zip` files under `lib/` (e.g. a `lib/main.zip` alongside `lib/main.dart`, a `lib/core/theme.zip`, a `lib/core/theme/app_theme.zip` alongside live theme source). These are not part of the app's runtime architecture and should not be treated as such by a future session — they read as accidental or intentional backup/archive artifacts of unknown origin and intent, not build inputs or referenced assets (none appear in `pubspec.yaml` or any import). The three `lib/`-scoped zips above were removed by commit `bbf477c` ("chore: remove obsolete backup zip files", 2026-09-26). A separate, much larger (~17MB) root-level `.zip` was then committed on 2026-09-30 (`498c412`) and is, as of this audit, deleted in the working tree but not yet committed as a deletion — see `KNOWN_ISSUES.md` for this recurrence. Their exact presence/absence in the working tree has changed between audits of this repository and should not be relied on as a stable fact; verify directly if it matters, and do not restore, delete, move, or otherwise act on them without an explicit instruction to do so.

## State Management Architecture

Package: `provider` (`ChangeNotifier` / `MultiProvider` / `ChangeNotifierProxyProvider`). No Riverpod, Bloc, or GetX.

All 12 top-level providers are registered in one place — `lib/main.dart:56-95`:

| Provider | Registration kind | Manages |
|---|---|---|
| `AuthProvider` | `.value` (constructed pre-`runApp`) | Session/auth state, sole owner of post-auth navigation |
| `NavigationProvider` | plain | Bottom-nav selected tab index |
| `PropertyProvider` | plain | Property search/listing state, pagination |
| `FilterProvider` | plain | Search/filter/sort params only — never calls services itself |
| `ShortlistProvider` | plain | In-memory shortlisted-property id set |
| `CompareProvider` | plain | Compare-properties id set, deliberately decoupled from Shortlist/Property providers |
| `ReelsProvider` | plain | Reels feed state/filters/interactions |
| `ProjectsProvider` | plain | Like/save state for builder projects the viewer doesn't own |
| `AvailableLocationsProvider` | plain | Loads `available_locations` table once at construction |
| `RecentSearchesProvider` | ProxyProvider on `AuthProvider` | Recent-search list; storage backend switches signed-in vs anonymous |
| `VoiceAgentProvider` | ProxyProvider on `AuthProvider` | Voice-agent conversational state machine |
| `NotificationProvider` | ProxyProvider on `AuthProvider` | Notification Centre list/unread count/realtime channel — deliberately app-level so the header badge and the notifications screen share one channel |

Many additional feature/screen-scoped providers live under `lib/providers/` (e.g. `add_project_provider.dart`, `messaging_provider.dart`, `dashboard_analytics_provider.dart`) and are instantiated closer to their owning screens rather than at app level — not exhaustively traced. The architecturally durable fact is the app-level vs. screen-scoped ownership split, not an exact file count, which changes with every feature added.

## Navigation & Routing

Classic **Navigator 1.0 with named routes** — not GoRouter, not Navigator 2.0/`Router`. `lib/app_navigator.dart` defines a single global `GlobalKey<NavigatorState> appNavigatorKey` so code outside the Navigator subtree (AuthProvider, deep-link handler, PendingInvitationGate) can push routes without a `BuildContext`.

- `MaterialApp.onGenerateRoute` (`lib/app.dart:103-526`) is one large `switch (settings.name)` over ~50 named routes.
- **Feature-flag route gate runs first**: `LaunchFeatures.routeEnabled(settings.name)` (`lib/config/launch_features.dart`) redirects to `RoleHomeRouter` if the route belongs to a currently-disabled feature — applies to deep links, stale saved routes, and notification payloads, not just UI menu visibility.
- **Role-based route gates** wrap specific screens rather than checking role inline: `AddProjectRouteGate`, `PostPropertyRouteGate`, `InfluencerVideoRouteGate` — these exist because the voice agent can route directly to these screens for any authenticated user, and letting a wrong-role user reach `/post-property` would upload media before RLS ever rejects the insert.
- `PendingInvitationGate` wraps every screen via `MaterialApp.builder`, watches `AuthProvider.pendingTeamInvitations`, and silently pushes `/pending-invitation` the first time it's non-empty in a run (mirrors the web portal's `TeamInviteGate.tsx`).
- `CurrentRouteNotifier` (singleton `NavigatorObserver`) exposes the current route name to widgets living above the Navigator (e.g. `CompareFloatingBar`).
- `ManageDashboardDispatcher` is a thin role dispatcher behind `/manage-dashboard` shared by three separate UI entry points.

## Session Restoration / Splash Logic

1. `SplashScreen` shows for a fixed 3 seconds, then checks `SharedPreferences['onboarding_done']`. If unset/false → onboarding, always winning over any auth destination on a genuine first launch.
2. Otherwise it calls `AuthProvider.enableNavigation()` and does nothing else — from that point **`AuthProvider` is the single owner of where the user goes**.
3. `AuthProvider` is constructed before `runApp` and subscribes immediately to Supabase's `onAuthStateChange` (a `BehaviorSubject` that replays the most recent event, typically `initialSession`, to new subscribers) — profile resolution is often already in progress by the time Splash's animation finishes.
4. `_handleAuthState` branches on the Supabase `AuthState`: `passwordRecovery` → `/reset-password` directly; `session == null` → `AuthDestination.signedOut`; new identity → `_fetchUserProfile`; same-user re-fire (duplicate `signedIn`/`tokenRefreshed`) → coalesced onto any in-flight resolution, explicitly documented as a fix for a race observed on physical devices after OAuth/magic-link callbacks.
5. `_resolveProfileOnce` first calls an `isCurrentUserLive` RPC (guards against a cached-but-admin-deleted account), fetches the `profiles` row, and classifies it via `AuthResolver.classify` — a **pure function of the fetched profile row only**, deliberately never touching `SharedPreferences`, to avoid a "Home, then back to Sign In" bug class the code comments describe as having previously existed from two independently-deciding call sites.
6. No route/screen persistence exists — "session restoration" means only "is there a Supabase session, and what does the `profiles` row say."

## In-App Update Check

Added 2026-10-14. `HomeScreen`'s `initState` postFrameCallback (`lib/screens/home/home_screen.dart`) fires `InAppUpdateService.checkOnce(context)` alongside the existing `PremiumLaunchBottomSheet.showOnce(context)` call — same "safe to do now" moment, same once-per-session gating pattern. Android-only (silent no-op elsewhere); checks Google Play for a pending update via the `in_app_update` package and, if FLEXIBLE-eligible, downloads it in the background, prompting once ("Restart now"/"Later") only after the download fully completes. Never the IMMEDIATE (blocking) variant. Every failure mode (no Play Store, `flutter run`, sideloaded APK, no update, decline/cancel, platform error) is swallowed silently. Plugin calls are isolated behind `UpdateCheckClient` (`lib/services/update_check_client.dart`) so `InAppUpdateService` (`lib/services/in_app_update_service.dart`) is unit-tested with a fake client. Does not touch the separate `PackageInfo`-based About-dialog version display in `workspace_drawer.dart`. See `CHANGELOG.md` for the full entry, including a FakeAsync test-harness gotcha hit and fixed during development.

## Deep Links

Package: `app_links`. Only one explicit app-level handler: `lib/core/navigation/invite_deep_link_handler.dart`, targeting `https://propcid.com/accept-invite?...` links from the `invite-team-member` Edge Function. It ignores the URL's own query params — `PendingInvitationGate` resolves the same invitation server-side by the signed-in user's email instead. If the user isn't logged in, it does nothing (a brand-new invitee must sign in first).

Password-reset deep links are **not** handled by this handler — Supabase's own `AuthChangeEvent.passwordRecovery` event (raised internally by the SDK after it processes its own auth-redirect deep link) drives that path directly in `AuthProvider`.

Native Android/iOS deep-link registration (manifest intent-filters / `Info.plist` associated domains) — see `RELEASE_SAFETY.md`.

## Authentication

See `HIGH_RISK_AREAS.md` and `API_CONTRACTS.md` for full detail. Summary:
- Email/password via a `username-auth` Edge Function (resolves username-or-email server-side).
- Email signup via Supabase magic link (`signInWithOtp`, `shouldCreateUser: true`).
- Phone OTP via MSG91, proxied through a `send-otp` Edge Function — **not** Supabase's built-in phone auth (deliberate, per code comment).
- Google OAuth via `supabase.auth.signInWithOAuth`.
- Meta/Facebook OAuth exists but is **not a login method** — it connects a signed-in user's own Meta/Instagram Pages for social/ads features.
- `AuthProvider.logout()` is the single canonical logout path; every other call site routes through it.

## Backend Integration

**Hybrid, Supabase-primary.** Hundreds of direct `supabase_flutter` SDK calls (`.from(`, `.rpc(`, `.storage.`, `.functions.invoke(`) across roughly 90 Flutter source files under `lib/`. No separate custom EC2 REST API client layer is present in the Flutter code — the client talks to Supabase-compatible SDK/API contracts directly. Whatever infrastructure or reverse proxies sit behind the configured Supabase hostname cannot be determined from this repository alone. Google Maps/Places are the primary explicit third-party REST API integrations made directly by dedicated Flutter services, keyed with `GOOGLE_MAPS_API_KEY` — this is narrower than saying the app has zero other external network traffic; see `API_CONTRACTS.md` for the distinction between dedicated backend/API integrations vs. external browser navigation, share URLs, and generic media downloads.

~50 Postgres tables are read/written directly from the client; **Flutter code currently references 8 Supabase Storage bucket names**, including two private collaboration-marketplace buckets (`collab-onetime`, `collab-deliverables`) — this is what the client uses, not a proven complete server-side bucket inventory; 20+ Edge Functions provide server-side logic (OTP, payments, moderation, OAuth exchange, AI proxy). Full detail in `API_CONTRACTS.md`.

## Storage / Media

Single storage backend: Supabase Storage. **Flutter code currently references 8 Supabase Storage bucket names** — `property-media`, `avatars`, `documents` [private], `chat-media` [private, signed-URL only], `media-library`, `project-media`, `collab-onetime` [private, signed-URL only], `collab-deliverables` [private, signed-URL only] — this is the client's own usage, not a proven complete server-side bucket inventory. The `[private]`/`[signed-URL only]` labels describe the **client-observed/expected access contract** (which URL-resolution method the client uses for each bucket), not an independently verified read of the actual Supabase Storage policy — the real RLS/read policies live server-side and are not present in this repository; see `API_CONTRACTS.md` for the evidence-level distinction. A single central helper, `PublicMediaUrl.resolve()`, rewrites Storage public-object URLs onto an optional `MEDIA_URL` CDN host from `.env`. When `MEDIA_URL` is unset, `PublicMediaUrl.resolve` is a no-op — the active value for any specific release must be verified from that release's own environment/build configuration, not assumed from this document (this repository's own `.env` is a single working-tree snapshot, not proof of what any given release ships with). Full detail in `API_CONTRACTS.md` and `HIGH_RISK_AREAS.md`.

## Roles

The live registration/routing model is **single-axis**: `profiles.user_type` ∈ `{individual, builder, broker, influencer}` (customer-facing, settable via the app) plus server-only `team_member`, `admin`, `super_admin`. `AuthResolver.classify` is the single source of truth for turning a profile row into a registration/routing destination, based on `user_type` + `profile_complete` — `profiles.user_role` plays no part in that classification.

The buyer/seller RBAC architecture built around `user_role` (`RBACService`, `RoleGuard` widgets, `ProfileCompletionCoordinator`, and the 3 unreachable `profile_completion/*_profile_screen.dart` files) is largely orphaned — see `KNOWN_ISSUES.md` KI-5. However, `user_role` is **not entirely dead**: it is still read by a few current staff-admin checks (`property_service.dart:1620-1638`, `social_campaigns_screen.dart:48-58`), inconsistently with other staff-admin checks that read `user_type` instead — see `KNOWN_ISSUES.md` KI-6 for the specifics.

## Main Business Domains

- **Property/Listing**: 5 categories (residential, commercial, land, pg, other), 8-step + review wizard, deliberately ported field-for-field from the React portal (`claude.md` governs this workstream). See `MODULE_MAP.md`.
- **Builder Projects**: model/service/wizard/inventory/offers/team system — more fully built than `docs/BUILDER_FLOW_IMPLEMENTATION_PLAN.md` currently states (that doc is stale).
- **Messaging**: DMs + Channels, realtime via 3 independent Supabase Realtime subscriptions, collaboration-marketplace messaging gated behind a feature flag.
- **Network/Social**: relationships (`builder_networks`), invitations, people search, network analytics/communication.
- **Payments/Subscriptions/Collaboration**: the Flutter client-side Razorpay integration is implemented and wired (screens, provider, service, checkout session), currently compile-time gated OFF in the Play release build config. The client never sends a price — server-side price resolution and order verification are Edge Functions whose source is absent from this repository, so server-side completeness/correctness/production-readiness cannot be independently verified from here.
- **Voice AI Agent**: `lib/voice_agent/` — LLM chat + STT/TTS proxied through a Supabase Edge Function, **31** registered tool names (every `toolRegistry.register(...)` call site): 24 real action/navigation tools (1 `navigate`, 2 search/compare, 1 favorites, 12 profile/account, 8 property/listing) + 7 sentinel/state-machine utility tools (`confirm`, `unknown`, `ask_platform`, `auth_required`, `suggest_signup`, `ask_about_platform`, `ask_property_info` — no-ops whose only purpose is making `toolRegistry.has(name)` true; `VoiceAgentProvider`'s own state machine handles them, never `.execute()`). **As of 2026-09-30, the entire feature is gated behind `FEATURE_VOICE_ASSISTANT`** (see Feature Flags below) — disabled in the Play release config, enabled in `full_development.json`; when disabled, tool registration never runs and `VoiceAgentProvider` is never constructed, not just hidden. Full breakdown in `MODULE_MAP.md`.

## Feature Flags

Single mechanism: `lib/config/launch_features.dart`, four compile-time `bool.fromEnvironment` flags (`FEATURE_SUBSCRIPTIONS`, `FEATURE_PAID_COLLABORATIONS`, `FEATURE_META_PUBLISHING`, and — added 2026-09-30 — `FEATURE_VOICE_ASSISTANT`), all defaulting `false` (fail-closed). Set at build time via `--dart-define-from-file` against `config/features/play_release.json` (all false) or `config/features/full_development.json` (all true). No remote-config service exists.

**The four flags are not enforced identically**: `FEATURE_SUBSCRIPTIONS` and `FEATURE_META_PUBLISHING` each have a dedicated named-route set (`_subscriptionRoutes`, `_metaRoutes`) checked by `LaunchFeatures.routeEnabled()` at the single `onGenerateRoute` choke point. `FEATURE_PAID_COLLABORATIONS` has **no equivalent route set** — it's enforced entirely by scattered call-site checks across messaging/notification/profile providers and screens instead. `FEATURE_VOICE_ASSISTANT` is neither route-gated nor call-site-scattered — it wraps the app-wide `FloatingAiOrb` overlay, the `VoiceAgentProvider` registration, and `_registerVoiceAgentTools()` itself in `lib/main.dart`/`lib/app.dart`, plus the auth screen's "Need help?" footer, so a disabled build never constructs the provider or registers a tool at all (not just hides UI for it). The fail-closed `defaultValue: false` behavior is identical for all four. Full detail in `HIGH_RISK_AREAS.md` / `KNOWN_ISSUES.md` / `RELEASE_SAFETY.md` / `DECISIONS.md`.
